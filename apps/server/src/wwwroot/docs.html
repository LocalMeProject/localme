معرفی و معماری پلتفرم لوکال‌می (LocalMe BaaS)

پلتفرم لوکال‌می یک زیرساخت جامع Backend-as-a-Service چندمستاجره (Multi-Tenant) بومی است که با هدف ارتقای چشمگیر سرعت توسعه اپلیکیشن‌های موبایل (Android, iOS) و وب‌اپلیکیشن‌ها پیاده‌سازی شده است. این سامانه توسعه‌دهندگان را از مدیریت سرورها، کانفیگ پایگاه داده، پیکربندی پیامک، و ستاپ باکت‌های ذخیره‌سازی کاملاً بی‌نیاز می‌سازد.

اصول کلیدی معماری لوکال‌می

  • ایزولاسیون بر پایه اسکیما (Schema-per-Project Isolation): هر پروژه دارای یک اسکیمای کاملاً مجزا در پایگاه داده PostgreSQL است. داده‌های مستاجران مختلف تحت هیچ شرایطی با یکدیگر تداخل نداشته و از بالاترین سطح امنیت و پرفورمنس برخوردارند.
  • کلیدهای تفکیک‌شده به ازای هر سرویس (Per-Service Scoped Keys): برخلاف سیستم‌های قدیمی که از یک کلید عمومی سراسری استفاده می‌کردند، لوکال‌می برای هر سرویس یک کلید مستقل با ساختار lm_[service]_[project]_[id] صادر می‌کند. در صورت افشای کلید یک سرویس، سایر سرویس‌ها ایمن می‌مانند.
  • ناوبری مدرن کلیکی سایدبار (Unified Click-based Navigation): سایدبار کنسول به صورت یکپارچه و دومرحله‌ای طراحی شده است. کلیک بر روی منوی سطح یک بدون تغییر صفحه، منوی سطح دو را به همراه دکمه بازگشت (در بالا برای دسکتاپ و در پایین برای موبایل) نمایش می‌دهد تا تجربه کاربری کامپکت و ارگونومیکی بدون هاورهای تصادفی فراهم گردد.
  • مینی‌پروفایل نوار بالا و نمایش موجودی لحظه‌ای: نوار بالای کنسول اطلاعات حساب و موجودی زنده کیف پول (مثلاً سینا والی زاده | ۱,۰۰۰,۰۰۰ تومان) را همواره در دسترس قرار داده و با کلیک، پاپ‌اور پروفایل، نشان نقش کاربری و پنجره‌های شارژ شتاب را در اختیار قرار می‌دهد.
  • راه‌اندازی تمیز بدون دیتای دمو (Clean Initial Boot): سامانه هنگام اجرا فقط ۳ کاربر پیش‌فرض پلتفرم را برای ورود با نقش‌های مختلف آماده دارد و هیچ پروژه، جدول یا رکورد نمایشی و فیک را از پیش تولید نمی‌کند.
  • محاسبه مصرف دقیق و اعتباری (Pay-As-You-Go Ledger): مصرف منابع (تعداد کوئری‌ها، پیامک‌ها، حجم فایل‌ها و زمان پردازش توابع) با دقت میلی‌ثانیه‌ای و ریالی در یک دفترکل دوبل حسابداری ثبت و از کیف پول کسر می‌گردد.

چرخه کار توسعه‌دهنده

  1. عضویت و ورود با شماره همراه در سامانه لوکال‌می.
  2. ایجاد یک پروژه جدید در کنسول توسعه‌دهندگان (هر توسعه‌دهنده در ابتدا با ۰ پروژه شروع می‌کند).
  3. ورود به صفحه اختصاصی هر سرویس در منوی کناری، تنظیم پارامترها و فعال‌سازی آن سرویس.
  4. کپی کردن کلید دسترسی اختصاصی همان سرویس و ارسال درخواست از اپلیکیشن کلاینت.

احراز هویت و ساختار کلیدهای دسترسی API

تمامی درخواست‌های ارسالی از سمت کلاینت‌ها (موبایل و وب) باید احراز هویت شوند. هدرهای استاندارد زیر برای برقراری ارتباط با پلتفرم الزامی هستند:

نام هدر (Header) مقدار الزامی توضیحات
x-api-key lm_[service]_[proj]_[id] کلید اختصاصی سرویسی که قصد فراخوانی آن را دارید.
Authorization Bearer <JWT_TOKEN> توکن احراز هویت کاربر نهایی اپلیکیشن (برای دسترسی‌های کاربرمحور).
Content-Type application/json قالب ارسال داده‌ها در متدهای POST و PUT.

قالب نام‌گذاری کلیدهای اختصاصی سرویس‌های ۴گانه

فرمت کلیدهای APISPECIFICATION
// ۱. پایگاه داده رابطه‌ای
lm_database_proj_xxxxxxxx_xxxxxxxxxxxx

// ۲. احراز هویت جامع کاربران
lm_auth_proj_xxxxxxxx_xxxxxxxxxxxx

// ۳. ذخیره‌سازی ابری فایل
lm_storage_proj_xxxxxxxx_xxxxxxxxxxxx

// ۴. توابع سرورلس لبه شبکه
lm_functions_proj_xxxxxxxx_xxxxxxxxxxxx

ورود به پنل کاربری، رمز عبور و دسترسی اختصاصی تک‌پروژه

کنسول لوکال‌می (/panel و /auth) سه متد احراز هویت مستقل را متناسب با نیازهای توسعه‌دهندگان، تیم‌ها و کارفرما ارائه می‌کند:

۱. احراز هویت پیامکی (SMS OTP - روش پیش‌فرض)

روش پیش‌فرض و توصیه شده برای توسعه‌دهندگان ایرانی. ارسال کد ۶ رقمی امن از طریق سرشماره‌های اختصاصی خدماتی:

POST /_baas/v1/auth/otp/request

تایید و دریافت توکن نشست:

POST /_baas/v1/auth/otp/verify

۲. ورود با نام‌کاربری و کلمه عبور اصلی (Platform Credentials)

دسترسی جامع و نامحدود به تمامی پروژه‌های تحت مالکیت کاربر در پنل لوکال‌می. شما می‌توانید با استفاده از نام کاربری، ایمیل، یا شماره تلفن همراه به همراه کلمه عبور وارد شوید.

POST /_baas/v1/auth/login
JSON PayloadREQUEST
{
  "username": "sina", // یا ایمیل یا شماره موبایل
  "password": "developer123456"
}

۳. ورود اختصاصی تک‌پروژه با رمز مجزا (Project-Scoped Access)

در مواقعی که می‌خواهید دسترسی پنل یک پروژه خاص را در اختیار فریلنسر، همکار یا کارفرما قرار دهید بدون اینکه به سایر پروژه‌ها، کیف پول یا اطلاعات کلی حساب کاربری شما دسترسی داشته باشد، می‌توانید در تب «تنظیمات پروژه» یک رمز عبور اختصاصی برای پروژه تعیین کنید.

کاربر با داشتن Project Slug و رمز پروژه، مستقیماً وارد محیط ایزوله همان پروژه می‌شود:

POST /_baas/v1/auth/project-login
JSON PayloadREQUEST
{
  "projectSlug": "my-online-shop",
  "password": "ProjectSecretPass2026!"
}

مدیریت رمز پروژه از طریق وب‌سرویس REST

تنظیم یا تغییر رمز عبور اختصاصی پروژه:

POST /_baas/v1/projects/{projectId}/password
JSON PayloadREQUEST
{
  "password": "NewProjectSecretPass"
}

حذف رمز عبور اختصاصی پروژه (غیرفعال‌سازی ورود مستقیم):

DELETE /_baas/v1/projects/{projectId}/password

دستورات CLI و راه‌اندازی سریع پروژه (Scripts)

جهت سهولت توسعه و استقرار محلی و پروداکشن، اسکریپت‌های زیر در package.json تعبیه شده‌اند:

ترمینال / CLIBASH
# راه‌اندازی سرور در محیط توسعه (Dev Mode)
pnpm dev
# معادل دستور: dotnet run --project apps/server/src/LocalMe.Server.csproj

# ساخت نسخه پایانی و اجرای پروداکشن (Release Mode)

# معادل دستور: dotnet run --project apps/server/src/LocalMe.Server.csproj --configuration Release

# اجرای کلیه تست‌های واحد و یکپارچگی (.NET 10)
pnpm test
# اجرای ساخت کامل مونوریپو

زیرساخت شبکه، دیتاسنتر و اتصال شاپرک

تمام سرورهای لوکال‌می در مراکز داده داخلی مستقر در منطقه تهران (ir-central-tehran) میزبانی می‌شوند.

  • IP خروجی ثابت و حاکمیتی (Egress NAT): 2.180.12.94 — تمامی ارتباطات با وب‌سرویس‌های شاپرک، سرشماره‌های پیامکی، و سازمان‌های دولتی از این آدرس IP ثابت انجام می‌پذیرد.
  • پایداری شبکه ملی اطلاعات: در شرایط اختلال اینترنت بین‌الملل، دسترسی کاربران داخلی به پلتفرم و اپلیکیشن شما به صورت ۱۰۰٪ پایدار و بدون وقفه برقرار می‌ماند.

۱. سرویس پایگاه داده رابطه‌ای (PostgreSQL & PostgREST)

این سرویس جداول دیتابیس پروژه را مستقیماً به صورت RESTful در اختیار کلاینت قرار می‌دهد. نیازی به نوشتن کنترلرهای اضافه در بک‌اند نیست.

اندپوینت‌های عملیاتی پایگاه داده

GET /_baas/v1/{projectId}/db/{tableName}

دریافت رکوردهای جدول به همراه قابلیت فیلترگذاری و صفحه‌بندی (مسیر هم‌ارز: /_baas/v1/{projectId}/rest/{tableName}).

POST /_baas/v1/{projectId}/db/{tableName}

درج یک رکورد جدید در جدول مشخص‌شده.

POST /_baas/v1/{projectId}/db/tables

ایجاد جدول جدید در اسکیمای پایگاه داده با ارسال {"name": "orders"}.

PUT /_baas/v1/{projectId}/db/{tableName}/{id}

ویرایش و به‌روزرسانی مقادیر یک رکورد بر اساس شناسه.

DELETE /_baas/v1/{projectId}/db/{tableName}/{id}

حذف قطعی یک سطر از جدول.

۲. سرویس احراز هویت جامع کاربران (Auth Service)

سامانه یکپارچه احراز هویت با پشتیبانی همزمان از پیامک یکبارمصرف (SMS OTP)، نام‌کاربری و رمز عبور (Credentials)، و ورود با شبکه‌های اجتماعی (OAuth 2.0 گوگل و گیت‌هاب).

قوانین رگولاتوری پیامک در ایران: برای جلوگیری از سوءاستفاده و رعایت الزامات قانونی رگولاتوری مخابرات، ارسال پیامک صرفاً از طریق کلید API و خط اختصاصی ثبت‌شده خود توسعه‌دهنده (کاkeptت، ملی‌پیامک، یا مگفا) که در تنظیمات سرویس احراز هویت ذخیره می‌شود، انجام می‌پذیرد.

الف) احراز هویت پیامکی (SMS OTP)

۱. درخواست ارسال کد تایید یکبارمصرف به شماره کاربر:

POST /_baas/v1/{projectId}/auth/otp/request
JSON PayloadREQUEST
{
  "phone": "+989121112233"
}

۲. تایید کد پیامک‌شده و دریافت JWT Token معتبر:

POST /_baas/v1/{projectId}/auth/otp/verify
JSON PayloadREQUEST
{
  "phone": "+989121112233",
  "code": "489201"
}

ب) ثبت‌نام و ورود با ایمیل و رمز عبور (Password)

۱. ثبت‌نام کاربر جدید:

POST /_baas/v1/{projectId}/auth/signup
JSON PayloadREQUEST
{
  "email": "user@example.com",
  "password": "StrongPassword123!",
  "name": "سارا محمدی"
}

۲. ورود و دریافت جلسه احراز هویت:

POST /_baas/v1/{projectId}/auth/login
JSON PayloadREQUEST
{
  "email": "user@example.com",
  "password": "StrongPassword123!"
}

ج) تبادل توکن احراز هویت ثالث (OAuth 2.0)

POST /_baas/v1/{projectId}/auth/oauth/{provider}

مقدار provider می‌تواند google یا github باشد. بدنه درخواست:

JSON PayloadREQUEST
{
  "code": "4/0AfgeXvu...",
  "redirectUri": "https://myapp.com/auth/callback"
}

د) مدیریت کاربران پروژه

دریافت لیست کاربران احراز هویت شده پروژه: GET /_baas/v1/{projectId}/auth/users

ثبت مستقیم کاربر از سمت کلاینت دارای دسترسی: POST /_baas/v1/{projectId}/auth/users

۳. سرویس ذخیره‌سازی ابری فایل (Object Storage)

سامانه نگهداری فایل‌های چندرسانه‌ای، کاتالوگ محصولات و اسناد با تفکیک باکت‌های عمومی (Public) و محرمانه (Private).

مدیریت باکت‌ها

دریافت فهرست باکت‌های فعال: GET /_baas/v1/{projectId}/storage/buckets

ایجاد باکت جدید: POST /_baas/v1/{projectId}/storage/buckets با بدنه {"name": "assets", "isPublic": true}

آپلود فایل (Multipart Upload)

POST /_baas/v1/{projectId}/storage/{bucketName}/upload

هدر الزامی: x-api-key: lm_storage_... و ارسال فایل در فیلد file از نوع فرم چندبخشی (multipart/form-data).

دریافت و استریم مستقیم فایل

GET /_baas/v1/{projectId}/storage/{bucketName}/{fileName}

۴. توابع سرورلس لبه شبکه (Serverless Edge Functions)

اجرای کدهای جاوااسکریپت خالص در موتور ایزوله و پرسرعت Jint. ایده‌آل برای منطق تجاری سمت سرور، فرمول‌های قیمت‌گذاری، اعتبارسنجی کدملی، نرمال‌سازی داده‌ها یا اتصال وب‌هوک به سرویس‌های ثالث.

استقرار و مدیریت توابع

دریافت فهرست توابع مستقر: GET /_baas/v1/{projectId}/functions

استقرار یا به‌روزرسانی کد تابع: POST /_baas/v1/{projectId}/functions با بدنه {"name": "محاسبه کرایه", "slug": "fare-calc", "script": "..."}

فراخوانی و اجرای تابع

POST /_baas/v1/{projectId}/functions/{funcSlug}/invoke

مسیر هم‌ارز: /_baas/v1/{projectId}/functions/{funcSlug}/exec. نمونه ورودی و خروجی:

JSON Payload (Context)REQUEST
{
  "distance_km": 15,
  "service_type": "vip"
}
JSON ResultRESPONSE
{
  "status": "success",
  "output": {
    "status": "ok",
    "distance_km": 15,
    "cost_irr": 375000,
    "cost_toman": 37500
  },
  "logs": [
    "محاسبه کرایه: مسافت 15 کیلومتر -> 375000 ریال"
  ],
  "latencyMs": 8
}

سیستم مالی، کیف پول و محاسبه مصرف (Billing & IPG)

لوکال‌می فاقد اشتراک ماهیانه اجباری است؛ هزینه خدمات صرفاً بر اساس مصرف واقعی از کیف پول اعتباری کسر می‌شود. کلیه مبالغ و تعرفه‌ها توسط سوپرادمین از پنل مدیریت قابل تنظیم هستند.

سرویس هستهواحد سنجشنرخ مصوب پیش‌فرض (ریال)معادل تومان
پایگاه داده رابطه‌ایهر ۱,۰۰۰ کوئری REST۱۰۰ ریال۱۰ تومان
احراز هویت کاربرانهر درخواست OTP / بررسی هویت۸۰۰ ریال۸۰ تومان
ذخیره‌سازی ابریهر گیگابایت در ماه۵۰۰ ریال۵۰ تومان
توابع سرورلس لبههر ۱۰۰ میلی‌ثانیه زمان اجرا۱۰ ریال۱ تومان

خطای اتمام موجودی (HTTP 402 Payment Required)

چنانچه موجودی کیف پول اعتباری به صفر برسد، درخواست‌های API با خطای 402 Payment Required مواجه خواهند شد. با افزایش اعتبار از طریق درگاه‌های معتبر شاپرک (سامان‌کیش، زرین‌پال، به‌پرداخت ملت) در کنسول، دسترسی بلافاصله احیا می‌گردد.

درگاه پرداخت شتاب و شبیه‌ساز کارت شاپرک

لوکال‌می مجهز به موتور اختصاصی تراکنش‌های شبکه شاپرک و درگاه‌های پرداخت اینترنتی (IPG) است که با PSPهای معتبر کشور (به‌پرداخت ملت، سامان‌کیش SEP، زرین‌پال و سداد) کاملاً یکپارچه شده است. همچنین جهت تست کامل چرخه تراکنش در محیط توسعه محلی بدون نیاز به کارت بانکی واقعی، یک شبیه‌ساز معتبر شاپرک ارائه شده است.

پاسخ وب‌سرویس حاوی authorityToken و paymentUrl جهت هدایت کاربر به درگاه (یا شبیه‌ساز محلی /_baas/v1/pay/mock-gateway?authority=...) است.

۴. پیکربندی حساب‌های پذیرندگی شاپرک (IPG Merchant Configuration)

لوکال‌می فیلدهای ۱ به ۱ و معتبر مستندات رسمی PSPهای شتاب را پشتیبانی و اعتبارسنجی می‌کند:

درگاه بانکی (PSP) پارامترهای فنی الزامی شاپرک پروتکل ارتباطی و ضوابط
به‌پرداخت ملت (Mellat) mellatTerminalId (عددی), mellatUserName, mellatUserPassword, mellatPayerId پروتکل وب‌سرویس SOAP/REST bpPayRequest شاپرک ملت
سامان‌کیش سپ (SEP) sepTerminalId (۸ رقم), sepMerchantId, sepCellNumber پروتکل توکنایزیشن درگاه سامان‌کیش با اعتبارسنجی کد پذیرنده
زرین‌پال (ZarinPal) zarinpalMerchantId (UUID استاندارد ۳۶ کاراکتری), zarinpalIsZarinGate, zarinpalSandbox وب‌سرویس REST API v4 زرین‌پال با پشتیبانی زرین‌گیت اختصاصی
سداد بانک ملی (Sadad) sadadMerchantId, sadadTerminalId, sadadTerminalKey (کلید متقارن Base64) پروتکل رمزنگاری متقارن شاپرک سداد بانک ملی ایران

۵. مسیریابی کلاینت و پیوندهای عمیق (Deep Linking & Client Router)

کنسول توسعه‌دهنده به عنوان یک پروژه یکپارچه ASP.NET Core بدون نیاز به دو استقرار مجزا (Next.js + Backend) کامپایل و مستقر می‌گردد. تمامی مسیرها بر روی سرور به کنترلر پنل متصل بوده و کلاینت با استاندارد HTML5 History API آدرس‌ها را مدیریت می‌کند:

  • /panel/{projectSlug}/overview/metrics: پیشخوان و سلامت زنده پروژه
  • /panel/{projectSlug}/db/tables: جداول داده و رکوردهای PostgREST
  • /panel/{projectSlug}/db/sqleditor: ویرایشگر تعاملی SQL
  • /panel/{projectSlug}/auth/users: کاربران احراز هویت شده
  • /panel/{projectSlug}/ipg/config: استودیوی درگاه پرداخت شتاب
  • /panel/{projectSlug}/telemetry/live: پخش زنده لاگ‌های سرور

با رفرش صفحه یا کپی کردن آدرس‌ها، کاربر دقیقا در همان پروژه و ماژول باقی مانده و حالت صفحه حفظ می‌شود.

۶. ذخیره‌سازی ابری پایدار بر زیرساخت ملی (Remote Persistence)

اطلاعات کنترل‌پلیین، کاربران، پروژه‌ها و تراکنش‌ها بر روی کلاستر اختصاصی PostgreSQL (پایگاه داده sina-infwqq_db) و کش توزیع‌شده Redis ثبت شده و با ریستارت یا ری‌لود سرور هیچ داده‌ای از دست نخواهد رفت. پروژه‌های جدید کاملا خام و بدون داده‌های نمایشی (Clean State) آغاز به کار می‌کنند.

سرویس جریان داده زنده و وب‌سوکت دوطرفه (Duplex Realtime WebSockets)

سرویس Realtime لوکال‌می یک خط لوله اختصاصی با پرفورمنس بسیار بالا بر بستر پروتکل استاندارد WebSocket ارائه می‌دهد که امکان پخش آنی تغییرات جداول دیتابیس (INSERT, UPDATE, DELETE)، برودکست رویدادهای سفارشی، سفارشات زنده، چت آنلاین و موقعیت پیک‌ها را بدون نیاز به ارسال درخواست‌های مکرر Polling برای اپلیکیشن‌های کلاینت فراهم می‌کند.

۳. مدیریت چالش‌ها و پایداری در شبکه‌های موبایل ایران (ISP Edge Cases)

چالش زیرساختی شبکه ایران علت و رفتار در اپراتورها راهکار و معماری لوکال‌می
NAT Timeout اپراتورهای موبایل ایرانسل و همراه اول سوکت‌های بدون دیتا را بعد از ۳۰ تا ۶۰ ثانیه به صورت خاموش قطع می‌کنند. ارسال فریم پینگ ضربان قلب {"action":"ping"} هر ۲۵ ثانیه توسط کلاینت به صورت خودکار.
جابجایی بین شبکه وای‌فای و سلولار آدرس IP کلاینت تغییر کرده و سوکت قدیمی در حالت تعلیق نامشخص (Silent Drop) باقی می‌ماند. شنود رویدادهای Connectivity سیستم‌عامل، بستن سریع سوکت مرده و اتصال مجدد با تاخیر نمایی (Exponential Backoff).
از دست رفتن اشتراک کانال‌ها پس از برقراری مجدد اتصال، سرور سوکت جدید را فاقد کانال‌های ثبت‌شده قبلی می‌شناسد. نگهداری لیست کانال‌ها در حافظه SDK کلاینت و ارسال مجدد فریم‌های subscribe بلافاصله بعد از رویداد onopen.
قطعی موقت اینترنت هنگام ارسال کاربر در نقطه کور آنتن قرار می‌گیرد و فریم‌های ارسالی با شکست مواجه می‌شوند. صف‌بندی آفلاین رویدادها (Offline Message Queue) در حافظه کلاینت و تخلیه ترتیبی پس از بازیابی لینک ارتباطی.

سامانه اعلان‌های هوشمند موبایل (Push Notifications Engine)

۳. نکات کلیدی و حالات مرزی (Edge Cases)

  • اعلان‌های پس‌زمینه خاموش (Silent Data Push): با ارسال فیلد data بدون title، اپلیکیشن به صورت نامرئی در پس‌زمینه بیدار شده و عملیات همگام‌سازی کش را انجام می‌دهد.
  • چرخش توکن (Token Rotation): کلاینت‌ها با ثبت لیسنر onNewToken، در صورت ابطال توکن قدیمی، توکن جدید را به سامانه ارسال کرده و رکورد قبلی اوررایت می‌شود.
  • پشتیبانی از چند ارائه‌دهنده (Failover): در صورت تاخیر یا مسدودی سرورهای FCM، لوکال‌می به صورت خودکار پِی‌لود را به درگاه دوم منتقل می‌کند.

اعتبارسنجی خریدهای درون‌برنامه‌ای بازار و مایکت (Mobile IAP)

جهت جلوگیری از کرک شدن اپلیکیشن‌ها و پرداخت‌های جعلی (Fake In-App Purchases)، اعتبارسنجی توکن خرید حتماً باید در سمت سرور انجام شود. موتور IAP لوکال‌می اتصال مستقیم امن با API توسعه‌دهندگان کافه‌بازار (Cafe Bazaar) و مایکت (Myket) برقرار کرده و توکن‌ها را اعتبارسنجی می‌کند.

۳. مکانیزم‌های دفاعی و مدیریت حالت‌های بحرانی (Security Guardrails)

// کلاینت جاوا اسکریپت / تایپ اسکریپت لوکال‌می
class LocalMeClient {
  constructor(projectId, keys) {
    this.projectId = projectId;
    this.keys = keys;
    this.baseUrl = 'https://api.localme.ir/_baas/v1';
  }

  // ۱. کوئری پایگاه داده
  async getRecords(table, params = {}) {
    const qs = new URLSearchParams(params).toString();
    const res = await fetch(`${this.baseUrl}/${this.projectId}/db/${table}${qs ? '?' + qs : ''}`, {
      headers: { 'x-api-key': this.keys.database }
    });
    return await res.json();
  }

  // ۲. احراز هویت پیامکی
  async requestOtp(phone) {
    const res = await fetch(`${this.baseUrl}/${this.projectId}/auth/otp/request`, {
      method: 'POST',
      headers: { 'x-api-key': this.keys.auth, 'Content-Type': 'application/json' },
      body: JSON.stringify({ phone })
    });
    return await res.json();
  }

  // ۳. ورود با ایمیل و پسورد
  async login(email, password) {
    const res = await fetch(`${this.baseUrl}/${this.projectId}/auth/login`, {
      method: 'POST',
      headers: { 'x-api-key': this.keys.auth, 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, password })
    });
    return await res.json();
  }

  // ۴. اجرای تابع سرورلس لبه
  async invokeFunction(slug, context = {}) {
    const res = await fetch(`${this.baseUrl}/${this.projectId}/functions/${slug}/invoke`, {
      method: 'POST',
      headers: { 'x-api-key': this.keys.functions, 'Content-Type': 'application/json' },
      body: JSON.stringify(context)
    });
    return await res.json();
  }
}
import requests

class LocalMeClient:
    def __init__(self, project_id: str, keys: dict):
        self.project_id = project_id
        self.keys = keys
        self.base_url = "https://api.localme.ir/_baas/v1"

    def get_records(self, table: str, params: dict = None) -> list:
        url = f"{self.base_url}/{self.project_id}/db/{table}"
        headers = {"x-api-key": self.keys.get("database")}
        r = requests.get(url, headers=headers, params=params)
        r.raise_for_status()
        return r.json()

    def request_otp(self, phone: str) -> dict:
        url = f"{self.base_url}/{self.project_id}/auth/otp/request"
        headers = {"x-api-key": self.keys.get("auth"), "Content-Type": "application/json"}
        r = requests.post(url, headers=headers, json={"phone": phone})
        r.raise_for_status()
        return r.json()

    def invoke_function(self, slug: str, context: dict) -> dict:
        url = f"{self.base_url}/{self.project_id}/functions/{slug}/invoke"
        headers = {"x-api-key": self.keys.get("functions"), "Content-Type": "application/json"}
        r = requests.post(url, headers=headers, json=context)
        r.raise_for_status()
        return r.json()
import 'dart:convert';
import 'package:http/http.dart' as http;

class LocalMeService {
  final String projectId;
  final Map<String, String> keys;
  final String baseUrl = 'https://api.localme.ir/_baas/v1';

  LocalMeService({required this.projectId, required this.keys});

  // ۱. دریافت رکوردهای جدول دیتابیس
  Future<List<dynamic>> getTableRecords(String table) async {
    final uri = Uri.parse('$baseUrl/$projectId/db/$table');
    final res = await http.get(uri, headers: {'x-api-key': keys['database'] ?? ''});
    if (res.statusCode == 200) {
      return jsonDecode(utf8.decode(res.bodyBytes)) as List<dynamic>;
    }
    throw Exception('خطا در دریافت اطلاعات: ${res.statusCode}');
  }

  // ۲. ارسال درخواست کد تایید پیامک
  Future<bool> requestOtp(String phone) async {
    final uri = Uri.parse('$baseUrl/$projectId/auth/otp/request');
    final res = await http.post(
      uri,
      headers: {'x-api-key': keys['auth'] ?? '', 'Content-Type': 'application/json'},
      body: jsonEncode({'phone': phone}),
    );
    return res.statusCode == 200;
  }

  // ۳. فراخوانی تابع لبه
  Future<Map<String, dynamic>> invokeFunction(String slug, Map<String, dynamic> context) async {
    final uri = Uri.parse('$baseUrl/$projectId/functions/$slug/invoke');
    final res = await http.post(
      uri,
      headers: {'x-api-key': keys['functions'] ?? '', 'Content-Type': 'application/json'},
      body: jsonEncode(context),
    );
    return jsonDecode(utf8.decode(res.bodyBytes)) as Map<String, dynamic>;
  }
}
